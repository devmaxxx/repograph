# 0.6.0 — Kotlin, measured before and after: design

Date: 2026-09-11. Base: `main` at `b21fb0f`, tagged `v0.5.0`. Nothing in this document is
implemented. The plan that executes it is
[`../plans/2026-09-11-0.6.0-kotlin.md`](../plans/2026-09-11-0.6.0-kotlin.md); the gates below are
copied, unedited, into the release's results document before any of them is read.

## What 0.6.0 is, and what it is not

Three pieces of work, in this order:

1. **The measurement debt 0.5.0 left.** Six gates are written and unread, and two of them are the
   baseline and the instrument every Kotlin reading is judged against.
2. **Kotlin**, on the pinned fixture's `mobile/` tree, under G6's gate and G1's symbol half.
3. **A release procedure that cannot lose its run to `[skip ci]` again**, which is how 0.5.0 was
   tagged with no release run.

The ledger promised C#, Kotlin and Python for 0.6.0. **This design ships Kotlin only.** The grammars
are not what holds the other two back: `tree-sitter-c-sharp 0.23.5` and `tree-sitter-python 0.25.0`
both build against `tree-sitter 0.27.0` and parse every construct they were sampled on. What holds
them back is G6's gate — a case file per corpus, committed beside its result — and there is no
corpus that gate can be committed for:

- `bonliva-crm-nx` is the only C# candidate: 1,176 `.cs` files, 395 of them generated. It is
  employer code, and a case file names its symbols in `devmaxxx/repograph`, which is public. Its
  documents carry Jira keys (`CRMDEV-`, 466 files) and no requirement ids, so its retrieval half has
  no family to census either.
- `bonliva-erp`, which G6 names as the Python corpus, holds 12 `.py` files, all incidental: skill
  helpers, one scratch file, one fixture generator.
- No other Python corpus exists on this machine.

Moving C# and Python to a later release is the first of the decisions listed at the end as Max's.

## 1 · The measurement debt, and why it goes first

Six gates are written and unread. Each is named in §10 of
`docs/bench/2026-09-10-next-version-levers-results.md` and in its ledger section. None needs a line
of product code. Every one needs the one writable worktree, `~/bench/beauty-crm-test`, reset by
`bench/probe/reset.sh`; G23 also needs a machine `bench/probe/quiet.sh` accepts.

| gap | what is unread | needs | price |
|---|---|---|---|
| G23 | the control: the same binary through `readers.sh` twice, inside the wall and RSS bars, and the `avg_cpu` spread | a quiet machine: on power, `quiet.sh` passing | one suite run twice, no tokens |
| G15 | the four recorded arms re-run, `anchors/<kind>` totals recorded through `bench/history/track.py` | the worktree | four `bench` runs, no tokens |
| G39 | Task 6: `graph.json` growth under the generic grammar, the one-file `update` wall, `graphdiff.py` against `main`'s build | a corpus build in the worktree | one build, no tokens |
| G34 | the corpus half: the bench line's `families=` clause on a corpus build | the same build as G39 | nothing extra |
| G32 | the fixture copy rebuilt, `enrich` run, the before and after arms read | the worktree | ≈ $0.20 of haiku |
| G19 | the embed cadence clauses on the small model | the worktree, `embed.sh` | one whole-store embed, ≈ 4.5 minutes |

One reading is added that no ledger section owns. **B0** is the blast suite on both corpora —
`bench/blast.jsonl` and `bench/corpora/beauty-crm-mobile/blast.jsonl` — run through
`bench/compare/run.py` with the `v0.5.0` binary, on the same day and the same machine as every
Kotlin reading after it. The last blast result files are from 2026-09-04 and a different binary;
the Kotlin gates below are stated against B0 and not against them.

**Why this is ahead of Kotlin and not beside it.** Kotlin puts new nodes into every list `ask`
fuses — its comments cite `FR-VIS-47`, `ADR-022` and more, so the id references move too — and the
four recorded arms can move the day it lands. A move can only be judged against a baseline read on
the same machine, with the same instrument, before the change. G15 and B0 are that baseline, and
G23 is what says a reader-row difference is a difference and not the machine. Read after Kotlin,
all three would be measuring the change they are meant to judge.

**Order inside the debt.** G23 first, because every later reader number is judged through its bars.
G15, G39, G34 and B0 share one reset and run next. G32 spends money and runs after the free
readings. G19 runs last and blocks nothing.

**Where it stops.** If `quiet.sh` refuses the machine three sittings running, G23 is recorded as
unread, the bars stay the 2026-09-07 ones, and Kotlin proceeds judged on counts alone, which do not
depend on machine noise. Its cost rows are then reported and not gated, and the results document
says so.

## 2 · The grammar

**`tree-sitter-kotlin-sg = "=0.4.1"`.** ABI 14, depends on `tree-sitter-language ^0.1` (the lock
already holds 0.1.8), MIT, released 2026-05-09 by ast-grep from fwcd's grammar line.

| crate | with tree-sitter 0.27 | why not |
|---|---|---|
| `tree-sitter-kotlin-sg 0.4.1` | builds, parses | chosen |
| `tree-sitter-kotlin-ng 1.1.0` | builds, parses | the fallback: Windows in its CI, but idle since 2025-01 with open misparses (`suspend`/`final`/`internal` as names, one-line members, several `catch` blocks) |
| `tree-sitter-kotlin 0.3.8` | no | depends on `tree-sitter >=0.21,<0.23` |
| `brokk-tree-sitter-kotlin 0.4.6` | no | pins `tree-sitter-language =0.1.7` against the lock's 0.1.8 |

**Census on the corpus, taken while planning.** Both candidates parse all 126 `.kt` files and all 14
`.kts` files in the fixture with zero `ERROR` and zero `MISSING` nodes, and both find 49 object
declarations against the 47 lines a grep for `object Name` finds. Neither is preferred by the
corpus; `-sg` is preferred by recency. A one-line `object Name { val x = 1 }` misparses in both as
an expression, silently; the corpus has no such line, and the limitation is written in the README's
language section rather than worked around.

**The risk is Windows.** `-sg`'s own CI runs Ubuntu only, so an MSVC build of its C parser is
unproven upstream. This repository's CI builds on `windows-latest` and `release.yml` can be
dispatched from a branch to build all three release targets without publishing. Both are gates.
If `-sg` fails on MSVC and `-ng` does not, `-ng` is taken and the census is re-run on it.

**A hand walk, not tag queries.** `tree-sitter-tags 0.27.0` works on this tree-sitter, and `-sg`
ships a `tags.scm` that loads. It is not used. A tags query yields definitions and nothing else:
no `Extends`, no annotations, no visibility, and not the declared type of a constructor `val` that
the calls pass resolves a receiver through. `-sg`'s query reports properties as constants and drops
an extension function's receiver. The TypeScript extractor is a hand walk over node kinds, and the
Kotlin one is the same shape so both are read the same way. No crate is added beyond the grammar.

**Node names are pinned by a dump, not by this document.** `dump_tree`
(`src/code/cases.rs:548`) picks its grammar from the file name it parses, so a `.kt` dump prints
the real shape of any construct before a case is written against it. The kinds quoted below are
what `-sg` 0.4.1 printed on a sample during planning: `package_header`, `import_header` with
`wildcard_import`, `class_declaration` (classes, interfaces, `fun interface`, enums, data, sealed
and annotation classes alike), `object_declaration`, `companion_object`, `function_declaration`
with a `receiver` field on extensions, `property_declaration`, `type_alias`, `primary_constructor`
and `class_parameter`, `delegation_specifier`, `annotation`, `modifiers` with
`visibility_modifier`/`platform_modifier`/`class_modifier`, `call_expression` over
`navigation_expression`/`navigation_suffix`, `this_expression`, `simple_identifier`,
`type_identifier`.

## 3 · Kotlin: the decisions

The graph does not change shape. Kotlin writes the node and edge kinds TypeScript already writes,
under the same id format, so `impact`, `trace`, `changes` and `ask` read it without a new code path.
What is new is a second grammar, an import resolver keyed by qualified name instead of by path, and a
dispatch that refuses to guess.

### K1 · A file with no grammar gets a file node and nothing else

`language_for` (`src/code/symbols.rs:9-15`) picks the TSX grammar for `.tsx` and the TypeScript
grammar for everything else. A repository that lists `**/*.kt` in `code_globs` today gets every
Kotlin file parsed as TypeScript: a normal-looking file node, symbols that are wrong or missing, no
imports, and no warning. Tree-sitter returns a tree with error nodes for any input, so the fallback
at `symbols.rs:177` never runs. The three passes each parse for themselves (`symbols.rs:177`,
`calls.rs:163`, `idrefs.rs:62`), so all three carry the same mistake.

`language_for` becomes `Lang::of(rel) -> Option<Lang>`. A file matched by `code_globs` whose
extension has no grammar gets one `File` node and nothing more, and `build` names the extensions it
indexed as files only on stderr, once. The JavaScript family — `.js`, `.jsx`, `.mjs`, `.cjs`, and
TypeScript's `.mts` and `.cts` — keeps the TypeScript grammar, which reads it correctly today; a
repository globbing `**/*.js` must not lose its symbols to a fix aimed at files nothing reads. This lands first and alone, before any Kotlin code: it is a
defect on `main`, it is language-independent, and it makes G1's lever — "a file the extractor
cannot parse still deserves a file node" — true in the graph rather than only in `changes`' output.

### K2 · The walk is the TypeScript one, re-homed

`src/code/kotlin/` holds the Kotlin arms of the passes `src/code/mod.rs` already runs —
declarations, calls, id references — writing into the same `Extraction`. `CodeExtractor::extract`
dispatches on `Lang` and the Kotlin path parses once per file; the TypeScript path keeps its three
parses in this release, so its output is not touched by a refactor nothing measured.

| construct | node | edge |
|---|---|---|
| `class`, `interface`, `fun interface`, `enum class`, `data class`, `sealed class`, `annotation class`, `object` | `Symbol` `sym:<rel>::<Name>` | `Declares` from the file |
| top-level `fun`, `val`, `var`, `typealias`, extension `fun` | `Symbol` `sym:<rel>::<name>` | `Declares` |
| members: `fun`, `val`/`var` in the body, `val`/`var` constructor parameters | `Symbol` `sym:<rel>::<Class>.<member>` | `Declares` |
| members of a `companion object`, named or not | `Symbol` `sym:<rel>::<Class>.<member>` | `Declares` |
| nested classes and objects, and their members | `Symbol` `sym:<rel>::<Outer>.<Inner>`, `…<Outer>.<Inner>.<member>` | `Declares` |
| `: Base()` and `: Interface` | — | `Extends` |
| `@Annotation` | `Symbol` `anno:<Name>` | `DecoratedBy` |
| a call to a local, same-package or imported function or class; `x.m()` and `this.x.m()` where `x` is a property or constructor `val` with a declared type; `Type.m()` on an object or a companion | — | `Calls` |
| `import a.b.C` | — | `Imports` to the declaring file, the imported names in the context |

Deliberate differences from TypeScript, each with its reason:

- **Visibility.** Kotlin is public by default, so the `Declares` context is `"export"` unless the
  declaration is `private` or `protected`. `internal` counts as exported, because a module boundary
  is not a file boundary.
- **Companion members belong to the class.** A caller writes `Outer.make()`, never
  `Outer.Companion.make()`, so the id a call resolves to and the id the declaration writes must be
  the same one.
- **Extension functions are named without their receiver.** `fun String.shout()` is
  `sym:<rel>::shout`. Two extensions of one name in one file collapse into one symbol, as TypeScript
  overloads already do in `CodeExtractor::extract`'s dedup.
- **Annotations point at `anno:<Name>`, not `deco:<Name>`.** The decorator namespace is global, and
  `apply_diff`'s co-declared closure (`src/main.rs:213-226`) re-reads every file sharing an id with
  a stale one: a Kotlin `@Inject` sharing `deco:Inject` with NestJS would chain every Kotlin file
  into every TypeScript update.

### K3 · Imports resolve through a declaration index, not a path

A Kotlin import names a qualified name, and the file declaring it is not named after it: in the
corpus `Tokens.kt` declares `SessionTokens`, and `ReplicaFiles` is declared by four files
(`expect` in `commonMain`, `actual` in `androidMain`, `iosMain`, `jvmMain`).

`Resolver::new` (`src/code/imports.rs:81`) already walks the repository once for `tsconfig.json`
and `package.json`. The same walk reads each `.kt` file's `package` header and top-level
declaration names into a map from `pkg.Name` to the files declaring it. Then:

- `import pkg.Name` resolves through the map to every declaring file;
- `import pkg.*` resolves a name when a call site uses it;
- a name declared elsewhere in the file's own package resolves with no import at all;
- `expect`/`actual` declarations resolve to every declaring file, each keeping its own id.

The index creates a staleness the path resolver never had: a declaration added to file B changes
what an unchanged file A resolves to. On `update`, when a `.kt` file is added or removed, or a
changed `.kt` file's top-level names differ from the `Declares` edges the graph holds for it, every
`.kt` file joins the stale set before `apply_diff`'s co-declared closure runs. A body-only edit, the
common case, re-reads that file alone.

Every Kotlin file, and not only the importers of the package, because the graph records no
package: tracking importers would need the previous run's index, which is not stored, and the price
of the wide rule is bounded by the Kotlin file count — 126 files here, about a seventh of a
`--no-dense build`'s 1.91 s — and paid only when a declaration appears, disappears or moves. The
one staleness left is a `package` line edited in place with every name kept; a moved file is a
removal and an addition and is covered. The one-file `.kt` update is a cost row below, so the
price is read rather than assumed.

### K4 · Nested members keep their container

`impact::container` (`src/impact.rs:73`) splits a member id at its first `.`, so
`Outer.Inner.method` would be changed through `Outer` rather than `Outer.Inner`. It splits at the
last `.` instead. `bare` (`:19`) keeps the first segment on purpose: a file exports its top-level
name, and a nested member is reached through it. TypeScript members are one level deep, so every
TypeScript id splits identically either way, and a test pins that before the change.

### K5 · The grammar generation moves

`walk::GRAMMAR` (`src/walk.rs:29`) goes from 1 to 2. A 0.5.0 store whose configuration listed `.kt`
holds TypeScript misparses under hashes that still match, and a 0.5.0 store on the default globs
holds no Kotlin at all; the bump makes the next `update` re-read the tree once, the path
`tests/grammar.rs` already covers. No store format changes: no node or edge kind is added, and the
`RGM2` mirror is keyed by the crate version and invalidated by every release anyway.

### K6 · What Kotlin does not include

- **`.gradle.kts` build scripts.** `**/*.kt` does not match them, the truth harness does not count
  them, and a build script's symbols are not what `impact` is asked about.
- **Kotlin/JS interop.**
- **Any edge between TypeScript and Kotlin.** The corpus has none to extract. The two sides meet
  through generated code and shared data: `apps/api/scripts/emit-openapi.ts` writes the OpenAPI
  documents the Gradle build feeds to openapi-generator; `packages/contracts/src/jcs.ts` and
  `Jcs.kt` share test vectors; `ConflictCode.kt` and `Matrix.kt` are generated from
  `conflict-codes.yaml`. A contract or codegen edge is a design of its own.

### K7 · Kotlin is on by default

`Config::default().code_globs` (`src/config.rs:72`) becomes `["**/*.ts", "**/*.tsx", "**/*.kt"]`,
and this repository's `repograph.toml`, which states every default as the README's worked example,
follows. A repository with no Kotlin sees no difference. A repository with Kotlin and no
`repograph.toml` — the pinned fixture is one — gains it on its first `update`, through K5's re-read.
If the retrieval gate below fails while the blast gates pass, K7 alone is withdrawn: Kotlin ships
behind an explicit `code_globs` and the README says so.

## 4 · The instrument

**Truth for a Kotlin `trace`.** `bench/compare/truth.py`'s `di_call_graph` (`:367-388`) reads only
TypeScript — `^export class`, `private name: Type`, `this.x.y(` — and runs over `apps` and
`packages`. It gains a Kotlin reader selected by extension, as `declarations` already is: a class
header with any of `public`, `internal`, `expect`, `actual`, `abstract`, `open`, `data`, `sealed`;
constructor and body properties `val name: Type`; calls `name.method(` and `this.name.method(`. The
roots gain `mobile`. The TypeScript truth file is byte-identical before and after, and a test in
`bench/compare/test_truth.py` pins that on a mixed fixture.

**Cases.** `bench/corpora/beauty-crm-mobile/blast.jsonl` gains three lines, each verified against
the fixture while planning:

- `trace` `SyncEngine` → `ReplicaFiles` via `RemoteWipeHandler`: `SyncEngine` holds
  `wipe: RemoteWipeHandler` and calls `wipe.execute()`; `RemoteWipeHandler` holds
  `files: ReplicaFiles` and calls `files.delete()`. `ReplicaFiles` is an `expect class` with three
  `actual`s, so the case exercises K3's last bullet.
- `trace` `SnapshotVerifier` → `SigningKeysSource` via `SigningKeyStore`: `keys.key(…)`, then
  `source.fetch()`; `SigningKeysSource` is a `fun interface`.
- `changes` from `68fff3a8~1`: 784 files in the window to the pin, 13 of them `.kt`, including the
  `expect`/`actual` secure storage and the Ktor client. 24 `.ts` files ride along to the pin, as in
  every `changes` window of this corpus, and the Kotlin gate reads the `.kt` rows only.

**Doc drift.** `docs/bench/three-graphs.md:50` and its `changes` row at `:61` still describe a
TypeScript-only truth; they are corrected in the same task as the reader.

**The `changes` score by language.** `bench/compare/run.py` scores a `changes` row as two totals,
files and symbols, and cannot say which language a miss belongs to — and every window in this
corpus carries both. Each row gains a `by_ext` object: the same four counts per file extension of
the file the truth attributes them to. The totals are unchanged, and a name the truth finds in both
a `.ts` and a `.kt` file counts once in each slot. This lands before B0, so the baseline and every
Kotlin reading are scored by one instrument.

**Where the Kotlin store lives.** In `~/bench/beauty-crm-test`, and never built from empty for the
retrieval arms. `reset.sh` runs with its default settle binary, the `repograph-main` every earlier
reading was reset with, so its settle walk finds nothing changed and its node and edge count check
passes. Then the branch binary runs one `update` in the worktree. That update re-reads the tree once (K5), adds the Kotlin nodes (K7), and embeds only the
new rows. TypeScript nodes keep the questions the fixture's store was enriched with; Kotlin nodes
have none, which is what a user upgrading an enriched store has, and G32's stderr line says so.
Every store image a comparison reads is copied to `~/bench/0.6.0-2026-09-11/log/<task>/<arm>/`
before anything else runs in the worktree.

edited after its number is read.

**Cost** — reported always, gated only when G23 was read:

- one-file `update` wall on a `.kt` file;

**Platforms.** `ci` green on `ubuntu-latest`, `macos-14` and `windows-latest` with the grammar in
the build, and `release.yml` dispatched from the branch green on all three targets.

**Where the branch stops.**

- A blast clause fails: Kotlin does not ship in 0.6.0. The readings are recorded and the ledger's

- The retrieval rule fails and the blast clauses pass: K7 is withdrawn, as §3 says, and the failing

- A cost row leaves its bars: recorded, and the release waits on Max.

## 6 · Shipping it

0.5.0 lost its release run to a `[skip ci]` in the squash body. GitHub skips a push-triggered
workflow when the pushed commit's message carries the marker anywhere, and a tag push is a push of
that commit. A squash merge copies every branch commit's message into the body, and the house
convention marks docs-only commits `[skip ci]`. Nothing failed and nothing ran; the release was
published by dispatching `release.yml` on the tag by hand, which publishes because the publish
steps test `startsWith(github.ref, 'refs/tags/')`.

A CI check that fails a PR carrying the marker would fight the convention on every docs commit, so
the fix is in the procedure, where the tag is made:

- **R1 · The release PR squashes with a written message.** The bump PR is merged with an explicit
  subject and body, not the concatenation GitHub offers.
- **R2 · The tagged commit is checked before its tag is pushed.** If
  `git log -1 --format=%B <sha>` matches `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]` or
  `[actions skip]`, the tag is pushed and `release.yml` is dispatched on it at once. Otherwise the tag
  is pushed and a `release` run for it must exist within two minutes, or it is dispatched then.
  Exactly one publishing run happens either way.
- **R3 · The binaries are proven before the number is spent.** `release.yml` dispatched from the
  branch builds, smokes and packs all three targets and publishes nothing. It runs on the release
  PR's head before the merge.
- **R4 · The bump.** `Cargo.toml`, `Cargo.lock`'s own entry, the `npm/*/package.json` files and the
  launcher's pinned optional dependencies, and the README status line, in the last PR before the
  tag.

`docs/bench/runbook.md` gains a release section holding R1 to R4 as commands.

## 7 · Decisions that are Max's

1. **C# and Python.** This design moves both out of 0.6.0, for the reasons at the top. The
   alternative is a corpus kept outside this repository with its cases kept beside it, which
   `bench/compare/run.py` supports through `--blast` but nothing records or publishes today.
2. **The Kotlin bars.** 18/20, 90% and 10% are this design's numbers, chosen before any Kotlin
   reading exists. They can be changed in review, and not after the results document commits them.
3. **`enrich` producing nothing.** It exits 1, the same status as a missing store. Moving it to 3
   matches `trace` and `bench`; it is a one-line change plus the campaign harness that reads the
   status. It is not in the plan unless chosen.
4. **Spending.** G13 (the code seat), G14 (the register prompt), G28 (the reranked p90 bar), G37 (a
   non-Claude model) and G25 (int8 weights on the default model) each need tokens, a download or a
   decision about a shipped constant. None is in the plan. G32's ≈ $0.20 of haiku is, because the
   rebuilt store it grades is the kind every Kotlin reading is taken on.

## 8 · Not in 0.6.0

- **G2**: nothing cheaper is left to try.
- **G22 and G24**: memory pressure, and the cross-encoder's pool depth.
- **G17**: matters only if the code seat is retried.
- **G33**: closed as accepted.
- **`impact --limit`, `changes --brief`, `ask --escalate`**: planned in the agent surface and never
  built, and no case asks for them.
- **One parse for the TypeScript path**: a refactor with nothing measured behind it.
- **A run on a real Windows machine**: still nobody's; CI and the dispatch run are the platform
  gates here.
