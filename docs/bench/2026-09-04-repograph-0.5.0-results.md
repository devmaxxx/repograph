## What moved, and what is not a delta

The brief for this run asked for one before-and-after table. Three of its rows cannot
be a before-and-after, and saying so is the point of the table rather than a footnote
to it.

| | 2026-09-03 (0.4.0 @ `7733bd53`) | 2026-09-04 (branch @ `502e8a6d`) | what to read |
|---|---|---|---|
| retrieval strict | 68/82 | 68/82 | unchanged. Nothing in this plan touched the retrieval path; the store is the same opus `enrich` |
| retrieval MRR | not a field | **0.635** | first measurement. The 2026-09-03 rows cannot be rescored — the harness stored no answer text — so there is no prior value and no delta |
| impact, files named | 110/114 (10 targets) | **123/123** (16 targets) | **not comparable.** Two independent denominator changes; see below |
| impact, cases | 10 | 16 | Task 5 added six narrow targets |
| trace | 8/8 | 8/8 | unchanged, 6/6 chains and 2/2 correct refusals |
| changes, symbols named | 32/43 (2 diffs @ `7733bd53`) | **1 783/1 844** (8 diffs @ `502e8a6d`) | **not comparable.** Different case count *and* a different corpus HEAD; see below |
| changes, files named | 13/20 (2 diffs @ `7733bd53`) | **498/498** (8 diffs @ `502e8a6d`) | **not comparable**, same two reasons. The file axis is at 100% on every one of the eight, against a denominator of the files the truth harness attributes a declaration to |
| `--rerank-local` paraphrase | not measured | 17/30 at 17.9 s a question | measured by Task 6 against its own control (15/30), not against 2026-09-03. Rejected; see below |
| Kotlin corpus, impact | did not exist | 0/20 over 8 targets | the intended baseline, not a failure |

**Why the impact fractions are not a delta.** The denominator moved twice, for reasons
that have nothing to do with each other. Task 3 stopped counting a symbol name that
appears inside a string literal as a reference to it, which removed three files from the
truth of the ten original targets — the truth was over-counting, and repograph had been
right to omit them. That takes those ten targets from 114 wanted files to 111. Task 5
then added six narrow targets, worth 12 more wanted files, for 123. On the ten targets
2026-09-03 measured, this run reads **111/111**; on the six new ones, **12/12**. The one
real recall gain in there is Task 4's: `AuthService`'s tenth file imported it through a
barrel, and `impact` now follows the re-export. So: one file found that was not found
before, three files that should never have been wanted, and twelve files from cases that
did not exist. `110/114 → 123/123` is not that sentence, which is why it is not written
as one.

**Why the changes fractions are not a delta.** A `changes` case's truth is the diff from
its base to the corpus's **live HEAD**, so every case's want-total grows as `beauty-crm`
moves forward on its own — the caveat is in
[`three-graphs.md`](three-graphs.md#caveats-that-belong-with-every-number). 2026-09-03
ran at `7733bd53`; this run is 36 corpus commits later, at `502e8a6d`, over four times as
many cases. The two `changes` cases that existed on both dates illustrate it: `cbc931ba~1`
wanted 5 symbols then and 21 now, `0f27d2d1` wanted 38 then and 54 now. Neither pair is a
measurement of the tool changing. Only the ratio within a single run means anything, and
only against another run at the same corpus commit.

## Retrieval — 82 questions

| | keyword | paraphrase | code | **strict** | soft | MRR | median ms | median chars |
|---|---|---|---|---|---|---|---|---|
| repograph | 40/40 | 16/30 | 12/12 | **68/82** | 80/82 | **0.635** | 389 | 606 |

Strict is identical to 2026-09-03, question for question in aggregate, and that is the
expected result: this plan changed the scorer, the blast truth and `changes` rendering,
and added an opt-in flag. It changed nothing on the path an `ask` takes.

**MRR is the new field, and it is what G5 asked for.** `rank` is 1 + the distinct
competing ids (for a file case, paths) a reader passes before the expected one; MRR is
the mean of `1/rank` with an absent id scored 0. Split by kind it says three different
things:

| kind | strict | MRR | at rank 1 | where the rest sit |
|---|---|---|---|---|
| keyword | 40/40 | 0.816 | 30/40 | 2–9, one case each at 5, 6, 7 and 9 |
| paraphrase | 16/30 | 0.247 | **2/30** | 7 at rank 2, 3 at rank 3, 3 at rank 4, 1 at rank 6, **14 absent** |
| code | 12/12 | **1.000** | 12/12 | — |

Code retrieval is not merely correct, it is first every time. Keyword is right every time
and top-of-answer three times in four. The paraphrase row is the one that changes an
argument: of the sixteen paraphrases whose id is present, **two** are at the top of the
answer. Fourteen are behind at least one neighbouring requirement, and fourteen more are
not in the answer at all. So the question G5 existed to settle — "is this a ranking
problem or a retrieval problem" — has both halves true, and neither half alone is the
story: reordering the answer cannot produce the fourteen ids that are absent, and finding
them would not by itself put them first.

**The file axis is complete on all eight**, which is what Task 2 was for: a hunk in a
file the graph never indexed used to be dropped, and is now printed as that file with
`not indexed` where a span would go. On 2026-09-03 the 18-file case named 11 of its 18
files; the same case today names 25 of 25. The two numbers are at different corpus
commits and so are not a delta.

**But that denominator is much narrower than "the files the diff changed", and the sentence
above is only true of it.** The `changes` file truth is
`truth["changes"][base]["code_files"]` (`bench/compare/truth.py:197`) — the files where the
TypeScript declaration regex attributed at least one symbol, not the files carrying hunks. On
base `bc9db289~1` **119 files have hunks and 18 are in the denominator**; the 101 excluded
include fifteen TypeScript files and nine of the sixteen Kotlin ones, which are precisely the
files Task 2 was written for. So 498/498 says repograph named every file the harness asked
about; it does not say it named every changed file. It very likely does — `touched` now emits a
`file:` id for every hunk whose file has no symbol — but that is not the measurement this
harness makes, and widening the denominator is a truth-side change with its own re-run.

**The 61 symbols not named, bucketed by the extension of the file that declares them:**
57 are Kotlin, 4 are one TypeScript name.

- **57 Kotlin declarations.** There is no Kotlin extractor before 0.6.0, so `touched`
  can name the `.kt` file but not the `fun` or `class` inside it. This is the whole of
  G1's symbol half and it is deferred on purpose.
- **4 × `LITERAL` in `packages/ui/test/no-raw-colours.test.ts`.** This one is the truth
  harness being wrong, not repograph. The declaration is
  `const LITERAL = /#[0-9a-f]{3,8}\b|oklch\(|rgb\(|hsl\(/i;` and `truth.py`'s
  `declaration_end` measures a declaration's extent by counting brackets, which a regex
  literal opens without closing: it gives `LITERAL` the span 28→105, the rest of the
  file, so every hunk below line 28 credits it. Four of the eight cases have such a hunk.
  Checked directly — repograph indexes a `const` with a regex initializer perfectly well
  (probed on a two-line throwaway repo), and it names the file's four other top-level
  consts in the same answer. It is the same class of defect Task 3 disclosed in
  `strip_comments`' docstring: a regex literal read as if it were code. Left unfixed
  here, deliberately — this run's job is to measure, and changing the truth would mean
  re-running it. It costs repograph 4 of 1 844 symbols, always in its own favour to fix.

## The cross-encoder — measured and not adopted

[ADR-001 Amendment 4](../adr/ADR-001-paraphrase-recall-was-a-prediction.md) is the
authority; it is summarised here because a result file that omitted it would read as
though the lever were still open.

| arm | keyword | paraphrase | code | p90 | mean s / question |
|---|---|---|---|---|---|
| control (this store, dense) | 40/40 | 15/30 | 12/12 | 226 | 0.06 |
| `--rerank-local`, depth 200 | 39/40 | 17/30 | 12/12 | 229 | 17.9 |

The rule was fixed before the run: the paraphrase floors move only on paraphrase ≥ 17/30
**with** keyword 40/40, code 12/12, p90 ≤ 230 and a *median* under a second. It clears the
paraphrase bar and fails two of the other four. The latency column is a mean, not that median:
no per-question distribution was captured, and the amendment says why the substitution cannot
change the verdict at this gap. Latency is the decisive failure and it is not close — 17.9 s a
question is eighteen times the bar, and four times what the remote `--rerank` pays. Keyword loses `NFR-STAFF-04`, and the amendment names the cause: the
candidate snippet is 120 characters and the sentence the question quotes begins at
character 139. **No floor moved. `--rerank-local` ships opt-in, as `--rerank` does.** The
control's 15/30 there and the 16/30 in this run's table are not two days apart — both ran on
2026-09-04. What differs is the corpus commit and the store refresh behind them: the
cross-encoder arm ran at `2483d932`, this run at `502e8a6d`, which is exactly the caveat this
document insists on for `changes`. Neither is a floor, and the shipped floors are unchanged:
14/30 paraphrase with embeddings for a store carrying generated questions, 9/30 for one without.

## What this run settles

1. **`impact` has no missing file on this corpus** — 123/123 over 16 targets, after one
   real fix (a barrel re-export is an importer) and one truth correction (a name inside a
   string is not a reference).
2. **`changes` no longer omits a file it cannot parse** — 498/498 files over 8 diffs, where
   the denominator is the files the truth harness attributes a declaration to, not every file
   the diff touched (see the `changes` section). The symbols inside those files are still
   missing and that is the 0.6.0 extractor's work.
3. **Ranking is measured** — MRR 0.635 overall, and paraphrase MRR 0.247 with 2 of 30 at
   rank 1, which is the number any future retrieval change has to beat.
4. **The one unmeasured retrieval lever is now measured and rejected**, so paraphrase
   recall at the zero-token budget is not waiting on an experiment anyone has skipped.
5. **Kotlin has a baseline of zero written down before the extractor exists.**

## Caveats that travel with these numbers

- One run per row, no repeats. For a fraction out of 30 the Wilson interval is wider than
  the gap between adjacent rows.
- Strict is a substring test; `rank` and `mrr` are what say where in the answer it sat.
  MRR has one run behind it and no prior value to compare against.
- A `changes` fraction is only comparable to another `changes` fraction at the same corpus
  commit. This one is `502e8a6d`.
- An `impact` truth is also recomputed from the tree and moves with it, though far more
  slowly than `changes` does.
- The retrieval numbers are this store's, and this store was built with an `enrich` pass
  on opus. The README's floors come in two sets — one for a store carrying generated
  questions, one for a store without them — and this store is of the first kind; nothing
  in this table is a floor either way.
- The corpus tree was not clean at run time (three agent-memory Markdown files under
  `.claude/`). They cannot reach any scored number, and no attempt was made to clean them.
- The binary is the branch, not a release: `--version` prints `0.4.0`.
- Two harness limitations are open and neither is corrected in the numbers above; both are
  written up in
  [`three-graphs.md`](three-graphs.md#caveats-that-belong-with-every-number). The `changes`
  truth does not blank comments and string literals the way the `impact` truth does, so a name
  appearing only in prose can sit in a case's expected symbol set — fixing it moves the symbol
  fractions in repograph's favour and needs a re-run to say by how much. And `ID_TOKEN`, the
  pattern that decides which ids compete for a rank, also matches `UTF-8`, `SHA-256`,
  `RFC-7807` and `ISO-8601`, so **the 0.635 MRR here may be pessimistic** by an unmeasured
  amount — the error cannot run the other way.
