# The residue, the seat and the register — three rules, written before the numbers

**Status:** pre-registered 2026-09-06, in the 0.5.0 line. Nothing in this document was measured
against a binary that carries any of the three changes; every number quoted is a baseline the
shipped binary at `origin/main` (`32577e2`) reads today, copied from a named file, and every number
the three rules will be judged on is unmeasured when this is written. The plan that executes it is
[`../plans/2026-09-06-residue-seat-register.md`](../plans/2026-09-06-residue-seat-register.md);
this document outranks the plan where they disagree, and no clause below is edited once a number
exists. A clarification, if one is needed, goes in the results document beside the number.

**Honesty clause, first.** Each of the three rules is written knowing something. For the residue
(G8), the coverage results document already names the property and already reports that on the
fixture it cost nothing measurable — so the rule below asks the fix to move *nothing*, which is
the strictest clause this project has, and the one a reader should expect a denominator change to
fail. For the seat (G13), the regenerated table already shows ten of thirteen `where` anchors in
the code list's top ten and A4's price of six held-out questions per arm under the old ratio; the
constant is derived by a procedure named here, not read off that table. For the register (G14),
an exploratory union of two generators' questions already read paraphrase 20/30 and `rule` 5/9 and
7/9 — numbers that ship nothing because no rule preceded them; the rule below is written for a
single generator and a set of clauses the union reading did not have. A reader who discounts each
result for the evidence its rule was written with is reading correctly.

## The order, and why it is not optional

Three changes, and one of them is upstream of another:

1. **The residue first.** `LexicalIndex::attainable` is the denominator of the coverage statistic,
   and the coverage statistic is what every constant in this document is a crossover of. Changing
   it after the seat's constant were derived would make that constant a number about a statistic
   that no longer exists.
2. **The seat second**, under whatever form the residue rule leaves — the fixed denominator if it
   ships, the shipped one if it does not. Its constant is derived only then.
3. **The register last in measurement.** It is a change to a store, not to the binary, and its
   numbers are a comparison of two stores read by one binary; the binary has to be the one the
   first two items leave. Its tokens can be spent as soon as this document is committed — the
   store is generated once and read later — but nothing about it is read before the binary is
   final.

If the order were reversed and the residue landed after the seat, everything the seat rests on
would be stale: the mixed held-out dumps carry `attainable_code` and `attainable_passages` under
the old denominator, so the crossover, the offline replay, the live measurement on `bc-a1`, the
replay check and the regenerated G13 table would all be re-derived and re-run under the new form,
and the seat's shipping decision re-taken. The register's numbers, if they had been read on an
earlier binary, would be re-read on the final one — both stores, both arms, both held-out sets —
because a comparison of two stores is only paired when one binary reads both.

## R — the residue of G8: what `attainable` charges

### What is wrong

`attainable(query)` sums idf over the unique query terms **present in that index**. A term the
questions index never saw leaves its denominator instead of lowering its score, so the list's
coverage — `best / attainable` — rises with every query term its index lacks. The form rewards an
index for a narrow vocabulary as much as for a good match. On the two-node test graph this is
exactly what seats the list the ratio refused; on the fixture it cost nothing the five clauses
measure. It is named in the coverage results and in ADR-001 Amendment 8, and left standing.

### Two designs weighed, one rejected outright

**A — every query term is charged; an absent term at the idf BM25 gives df = 0.** `attainable`
becomes the sum over every unique query term of `idf(n, df)`, with `df = 0` for a term the index
does not hold — `ln(2n + 2)`, the largest idf the index can express. The statistic stays a
property of the query and of one index alone; `search` is untouched, so no ranking moves; the
dump contract (`attainable_passages`, `attainable_questions`, `attainable_code`) keeps its three
fields and its meaning; an index over no documents attains nothing. Its cost: a term *no* index
holds is charged to every denominator in equal measure (the passage and questions indexes are
built over the same non-file nodes, so their `n` is equal), which pushes the two coverages' ratio
toward the ratio of the raw bests by a bounded amount — for a long developer question with
denominators near 110, one such term is about a tenth of each. The crossover is re-derived and
absorbs the average of that shift; the per-query shift is recorded.

**B — the store's vocabulary: only terms some index holds are charged.** As A, but a term absent
from both the passage and the questions index is dropped from both sums, so a word nobody could
answer does not move the admission at all. `Lexical` would carry the union of the two vocabularies
and `attainable` would take it. Its cost is on the code side: the code index's own vocabulary is
not in that union, so a term only the code index holds would be dropped from both denominators
while still scoring in the code list's best — the same residue, now rewarding the code list for
its *private* vocabulary, on the seat the next rule is about. Widening the union to the code index
makes the statistic depend on whether that index was built, which differs between a resident
`Context` on the plain path and `dump`, and clause 5 below would then judge the binary against a
replay of something else.

**C — a shared idf across the indexes** is rejected on scope: it changes `search`, so it changes
every ranked list and every floor, and the coverage form's premise — a statistic of one list
alone, ranking untouched — is what it would give up.

**The pick is A.** It removes the named residue on every list, including the code list's, with no
change to the dump contract and no dependence on which indexes a caller built. **B is the
fallback**: if A fails the rule below, B is tried under the same rule with its own crossover, and
its code-side residue is recorded as the reason it was second. If both fail, the residue stays
named and measured, `attainable` stays as shipped, and the seat is derived under the shipped
denominator.

### The arithmetic is part of the specification

The gate stays `f64` over `f32` inputs, as Amendment 8 requires, and `bench/admission.py` reads
the recorded `attainable_*` fields as before — the replay needs no new arithmetic, only the new
denominators the binary records. `search` does not change by a bit: every `bm25_*` and `dense_*`
list in every dump taken on the new binary is byte-identical to the shipped binary's, and that is
checked before any admission number is read.

### The constant

A new denominator is a new form, and a form's constant is the crossover of the 400 held-out
questions in the `--no-dense` arm, derived on dumps of the binary carrying the form before either
suite is opened — the procedure `bench/admission.py crossover` implements and the one 0.761 was
derived by. The constant this rule ships with is whatever that procedure returns, to three
decimals, not rounded and not tuned; if it returns 0.761 nothing moves. It is not compared with
0.761 and chosen; it is derived once.

### The rule

The fixed denominator ships if, and only if, **all seven clauses hold on the binary that carries
it**, under the constant derived above. Any one failing ends the design; the fallback is tried
once under the same clauses; a second failure leaves the residue as shipped.

0. **The constant is derived before either suite is opened**, on the new binary's held-out dumps
   in the `--no-dense` arm, and written to a file before `score` runs.
1. **No floor breaks.** Every floor `bench` grades holds in all four fixture arms — the two
   enriched arms on the fixture, the two raw arms on a raw copy of it — with p90 at or under 230.
2. **No arm loses ground on the recorded suite.** Subsumed by clause 6, stated so the five shipped
   clauses are all present.
3. **No arm loses ground on the developer suite.** Dense total at least 38, lexical at least 38,
   `where` no lower than 0/9 in either arm.
4. **No significant held-out loss.** Paired exact McNemar against the shipped binary's dumps, both
   arms, the same 400 questions; a loss at p < 0.05 is disqualifying, a wash passes.
5. **The replay still agrees with the binary.** `bench/admission.py check --form coverage` at the
   derived constant reproduces the binary on all three case sets in both arms — 82, 60, 400.
6. **The four recorded arms do not move.** The three counts of each recorded arm are identical to
   the baseline table above — `40/40 15/30 12/12`, `39/40 15/30 12/12`, raw `40/40 9/30 12/12` and
   `39/40 7/30 12/12` — with p90 at or under 230. Per-case movement inside an unchanged count is
   recorded, not judged.

### What is recorded either way

The crossover line and its four percentages; the per-query shift of each `attainable_*` field
between the shipped and the new binary, as a distribution per suite and per index; the six replay
lines; the four fixture arms and both developer arms; both held-out compares with their p-values;
and the G13 table regenerated under the new denominator, whether or not it ships.

## S — one seat for the code list (G13)

### What is wrong

`where` reads 0/9 in both arms and no admission form was ever going to move it: the code list
ranks ten of the thirteen `where` anchors in its own top ten, four at rank 1, and has no seat on
the plain path to say so. A4 priced one seat under the old ratio gate at `where` 0/9 → 2/9 and six
held-out questions lost in each arm, none gained, p = 0.031. It has never been read under the
coverage form, and never under a constant of its own.

### The shape

On the plain path, after the passage list, the code-questions list contributes **its top-ranked
document and nothing more** when the coverage admission seats it against the passage list —
`coverage(code) / coverage(passages) ≥ c_code`. `fuse::interleave` is a round-robin, so a
one-element list takes the slot its rank-one turn gives it and displaces no second document seed.
The reranked path is unchanged: it already pools the whole code list. A store without code
questions has no code index and is untouched by construction.

### The constant, and what it is derived on

The questions list's `c` is the crossover of 400 document questions between the questions list
and the passage list, two indexes over the same nodes. It is not reused here, and the reason is
base rates rather than units: the coverage form makes two lists' statistics comparable, but a
crossover is a procedure over a population, and the population the seat decides on is not the one
`c` was derived on. On document questions the code list never holds the answer; on code questions
the passage list holds a file never and a symbol rarely. A constant derived on documents alone is
degenerate toward "never seat" and one derived on code alone toward "always seat", and neither is
the question the seat asks, which is: *at what relative coverage is this query one the code list
answers rather than the passages?*

So `c_code` is the crossover, by the same procedure and in the same `--no-dense` arm, over a
**mixed held-out set on `bc-a1`**: the 400 document questions the fixture's set already is —
`bc-a1`'s document questions are the fixture's, verbatim — and 400 code questions drawn from
`bc-a1`'s 3,463 code entries, one per node, at the same seed 20260905, scored leave-one-out as
every held-out question is. The statistic per question is `coverage(code) / coverage(passages)`,
the split maximises the questions on the side of the list that holds their answer in its top
five, ties to the lower value. The one judgement in that procedure is the mix, and it is fixed
here at equal halves before any dump is taken: the developer suite is 24 file-anchored questions
of 60 and the recorded suite 12 of 82, and this document does not pretend to know the true share.
The constant is written to a file before the offline replay reads a suite, and is not compared
with `c`.

### The baseline

The seat is judged against the same binary with the seat off, on `bc-a1`, in both arms — the
binary rule R leaves, so the questions admission is identical on both sides and the seat is the
only difference. Those baselines are taken in the plan's Task 4, after rule R is settled, and are
not quoted here because they do not exist yet.

### The rule

The seat ships if, and only if, **all six clauses hold on the binary that carries it**, on
`bc-a1` with the seat on against the same binary with the seat off. Any one failing leaves
`CODE_SEAT` false, the path in the code for the next measurement, and `where` at 0/9 with the
price recorded.

0. **The constant is derived before either suite is opened**, from the seat-off mixed held-out
   dump in the `--no-dense` arm, and written to a file before `score` runs.
1. **No floor breaks.** Every floor holds on `bc-a1` in both enriched arms with p90 at or under
   230, and the fixture's four arms are unmoved — checked by comparing its dumps with the seat on
   and off, which must be byte-identical because the fixture has no code index.
2. **No arm loses ground on the recorded suite** on `bc-a1`: keyword, paraphrase and code each at
   least the seat-off count, both arms.
3. **The developer suite is not down and `where` moves.** Total at least the seat-off total in
   both arms, and `where` at least 1/9 in both arms.
4. **No significant held-out loss on the document questions.** Paired exact McNemar, seat off
   against seat on, the 400 document questions, both arms; a loss at p < 0.05 is disqualifying.
   This is the clause A4 failed, and the one the seat has to clear.
5. **The replay still agrees with the binary.** `bench/admission.py check --code-seat` at both
   constants reproduces the seat-on dumps on all four case sets in both arms — recorded 82,
   developer 60, document held-out 400, code held-out 400.

### Recorded, not deciding

The code held-out set before and after, with its McNemar — the gain the seat exists for, reported
beside the price; the G13 table regenerated under the shipped denominator and this constant; and
the one-shot lexical `ask` on `bc-a1`, which pays the code index build again on the plain path
once the seat is on — 18.5 ms when the 0.5.0 gap work measured the eager build, re-measured in
one sitting and reported as a cost, not judged.

### What ships and what does not

Pass: `CODE_SEAT = true` and `CODE_GATE = c_code` in `src/query.rs`, the resident context
building the code index for plain answers on a store that has code questions, and ADR-001
Amendment 9 carrying the numbers. Fail: `CODE_SEAT` stays `false`, `CODE_GATE` carries the derived
constant and its provenance in its comment, the override `REPOGRAPH_CODE_SEAT=1` stays for the
next measurement, and G13 records which clause and by how much.

## G — the register (G14)

### What is wrong

The second diagnostic found the cause of D1's `rule` loss in *how* a node's questions are written,
not in their shape and not in the model: one generator writes them in the asker's colloquial
voice, the other in the document's own precise one, and the share of a query's words found in its
node's questions moves −29% on `rule` and +32% on `long` between the two. The `rule` cases are the
only developer questions written in a person's permission-asking voice, and the only ones that
lose. The union of both registers, merged by a script at no model tokens, read paraphrase 20/30 in
both arms and `rule` 5/9 and 7/9 — exploratory, unruled, and favoured on held-out by holding the
fixture's own questions.

L4 as framed — a prompt per node kind asking for "is this allowed" questions — is retired here on
the record: it failed its own diagnostic gate on both readings (1 and 2 of 4 against a bar of 3),
and the second diagnostic shows it aimed at shape where the loss is register. `src/enrich.rs` was
never changed for it and no token was spent on it.

### The lever

Recommendation 1 of the second diagnostic, as written: **one generator**, the existing documents'
prompt asked to write **six of a node's twelve questions in the words the person asking would
use — first person allowed, and for an entry that decides or forbids something, the question of
someone about to do that thing — and the other six in the entry's own vocabulary, as now.** The
synonyms line, the four reader roles, the language rule and the output format are unchanged. The
exact wording is in the plan and in `src/enrich.rs`; as the prompt's own comment says, a
rewording is a re-measure, and this is that measure.

### The generator, and why it is the default one

The run is on the **default enricher** (`enrich_model = "haiku"` as `src/config.rs` ships it),
named explicitly in the copy's `repograph.toml`, with the prompt as the only variable against the
fixture — which was enriched by the same generator under the old prompt. A prompt that ships
becomes what every default `enrich` produces, and this project does not ship a configuration it
has not measured. A second run on the stronger generator, which is where the register loss was
observed, would isolate nothing against the fixture (two variables) and is priced but not run:
≈ $13.62 at D1's per-corpus figure, against ≈ $2.50 for this one. Both figures are estimates from
tee'd bytes and say so.

### The held-out set that decides

The fixture's held-out set was built from the fixture's own questions, and a question's twelve
siblings stay in its node when the question itself is held out, so the fixture has a home
advantage on it that a regenerated store does not. The second diagnostic named this and asked the
next attempt to judge on a set from a generator that is in neither store. That set exists at zero
tokens: **400 questions built from `bc-d1`'s questions at seed 20260905** — the same 400 anchor
nodes, since `bc-d1` carries the same 1,996 keys, and texts that neither the fixture nor the new
store holds, which is checked. Both stores are read on that set by the same binary, paired. The
fixture's own set is read as well and recorded, with its bias against the lever stated, and does
not decide.

### The rule

The register prompt ships if, and only if, **all six clauses hold**, the new store against the
fixture, both read by the final binary the plan leaves.

1. **No floor breaks.** Every floor holds on the new store in both enriched arms with p90 at or
   under 230.
2. **No arm loses ground on the recorded suite.** Keyword, paraphrase and code each at least the
   fixture's count on the same binary, both arms — 40/15/12 and 39/15/12 as the shipped binary
   reads them, re-read on the final one.
3. **The developer suite is not down and `rule` holds.** Total at least the fixture's in both arms,
   and `rule` at least 5/9 in both arms — the kind at risk, named before the run.
4. **No significant held-out loss on the neutral set.** Paired exact McNemar, fixture against the
   new store, the 400 `bc-d1`-built questions, both arms; a loss at p < 0.05 is disqualifying.
5. **The replay agrees with the binary** on the new store's dumps — the store behaves under the
   shipped admission like any other.
6. **The lever does what it is for.** At least one of: paraphrase above the fixture's count in
   either arm; the neutral held-out set significantly better in either arm; `rule` above 5/9 in
   either arm. A pass on clauses 1–5 that moves none of these is recorded as *no effect* and does
   not ship — a rewording measured to change nothing is not a reason to change the prompt every
   store is enriched with.

### What ships and what does not

Pass: the documents' prompt in `src/enrich.rs`, for every generator. **Not** the default model —
that is a cost decision this rule does not take. **Not** the floors — they are the fixture's
measured counts and the fixture is not re-enriched; the new store is kept as a durable copy and
its runs are recorded in the history under a tag of their own. The README's enrich paragraph says
what the prompt asks for and quotes the numbers. Fail: `src/enrich.rs` is reverted, the store copy
is kept for the next attempt, and G14 records the register prompt as measured on the default
generator and rejected, with the clause and the number. Either way, the register-share table —
the second diagnostic's metric, recomputed on the fixture, `bc-d1` and the new store — is
recorded, because it says whether the prompt moved register at all, which is the mechanism this
lever rests on.

## What these rules deliberately do not require

**Byte identity anywhere but where it is the point.** Rule R requires the ranked lists to be
byte-identical because the change is to a denominator and nothing else; it requires the arms'
counts to be identical because a corrected denominator that moves answers on this store has
changed something other than the residue. Rules S and G are meant to move answers, and require
that nothing gets worse.

**A single constant shared between the two admissions.** The 0.5.0 design proposed stage B under
"the same form and the same `c`, no second constant, because a constant chosen for the code list
by looking at the developer suite is how a suite stops measuring anything." The second half is
kept whole — no suite is read before either constant is fixed — and the first half is replaced by
a derivation, because a crossover is the procedure that makes a constant not a reading, and
reusing one across populations would be a reading after all.

## The token line

Model tokens are spent at exactly one point in the plan: the `enrich` of the register copy, on
the default generator, once — ≈ $2.50 estimated. Everything else — every dump, replay, bench,
held-out set, embedding and re-embedding — is zero tokens.
